# PROSTA 実装解説メモ

更新日: 2026-10-30

機能、認証・データ保護、JavaScript、CSSの「どう実装しているか」「なぜその方式か」を説明するための資料。
ソースを確認した時点の実装を記載する。対策が存在することと、あらゆる不正・障害を防げることは区別する。
作業の時系列は [作業ログ](./作業ログ_20261029.md)、本番のHTTPS構築は [HTTPS設定手順](./OCI_Apache_Tomcat_HTTPS設定手順.md) を参照。

## 1. 最初に説明するなら

> PROSTAは、Java/Spring Bootで処理し、ThymeleafでHTMLを生成する学習アプリです。
> 問題・解答履歴・ユーザー情報をDBへ保存し、履歴の集計から弱点、学習状況、実績などを表示します。
> JavaScriptは非同期API通信やモーダル、タイマーなどを担当し、CSSでPCと狭い画面の配置を切り替えます。
> 認証ではタブ別のセッション分離とDB上のログイントークンを組み合わせ、別ユーザーの混同と同一アカウントの古いログインからの更新を防ぎます。

## 2. 全体構成と処理の流れ

### 2.1 主な技術

- Java 17 / Spring Boot 3.1.5 / Spring MVC
- Thymeleaf: HTMLテンプレートへの値の埋め込み、共通部品の再利用
- Spring Data JPA / Hibernate: DBアクセス、Entityの変更保存、トランザクション
- Oracle: 本番の永続データ。今回の自動検証ではH2へ差し替えている
- JavaScript: 標準DOM API / fetch中心。一部はHTML内のインラインスクリプト
- JUnit / MockMvc: ロジック、API、画面テンプレート、認証フィルター込みの回帰テスト

### 2.2 1リクエストの流れ

```text
ブラウザーのリンク・フォーム・fetch
  -> タブIDの付与
  -> TabSessionFilter: タブのHttpSessionへ差替え、同一タブを直列処理
  -> LoginCheck: 公開URL・ログイン・管理者権限・送信元の確認
  -> SingleLoginFilter: 顧客行ロック、現在のログイントークンの照合
  -> Controller: 入力確認、対象の所有権確認、Service/Repository呼出し
  -> Service / Repository / Entity: 業務処理、DB検索・保存
  -> HTML描画またはJSON/リダイレクト
  -> DBトランザクション確定、必要に応じてAfterCommit処理
```

静的ファイル、公開URL、未ログインの要求は、各フィルターの除外条件に従う。
すべてのリクエストが必ず顧客行ロックを取るわけではない。

### 2.3 パッケージの役割

基準: [Javaソース](../src/main/java/jp/co/sss/pr/)

| 場所 | 役割 |
|---|---|
| `login_function` | ログイン・登録・ログアウト、タブ分離、アクセス制御、heartbeat |
| `mypage_function` | MyPage、履歴、学習状況、予定、フレンド、背景、実績、チャットの入口 |
| `test_function` | 出題選択、解答、確認、採点、結果表示 |
| `question_function` | 問題検索、管理者向け問題管理 |
| `user_function` | ユーザー更新、管理者のユーザー管理 |
| `service` | EXP・弱点・クエスト・チャット等の業務ロジック |
| `repository` | DB検索、ページ分割、件数・日別・カテゴリ別集計 |
| `entity` | テーブルとJavaオブジェクトの対応 |
| `form` / `bean` | 画面入力の受け取り、表示・セッション用データ |

Entityをそのまま全項目JSON化するのではなく、フレンドAPI等では必要な項目だけのrecordへ変換する。

## 3. 登録・認証・セキュリティ関連の実装

### 3.1 登録とユーザー名の重複

担当: [LoginController](../src/main/java/jp/co/sss/pr/login_function/LoginController.java)、[UserController](../src/main/java/jp/co/sss/pr/user_function/UserController.java)、[CustomerForm](../src/main/java/jp/co/sss/pr/form/CustomerForm.java)

- 新規登録: `existsByUserName`で同名の存在を確認する。
- 更新: `existsByUserNameAndUserIdNot`で本人以外との重複を確認する。名前を変えない更新は許可する。
- 更新確認時だけでなく確定時にも確認する。他の操作で状態が変わった可能性があるため。
- 現在のフォーム制限はユーザー名1～8文字、パスワード4～16文字の英数字。DBの名前列の長さ20とは別の制約。
- 論理削除ユーザーを除外した重複確認ではないため、削除済みの名前も使用済みとして扱う。
- 存在確認はアプリ側の検査であり、同時登録の原子的な一意性をそれだけで保証するものではない。DBの一意制約や並行要求については別の観点で確認する。

### 3.2 パスワード

担当: [PasswordService](../src/main/java/jp/co/sss/pr/service/PasswordService.java)

- 新規保存・更新はBCryptでハッシュ化し、照合はBCryptPasswordEncoderを使う。
- 暗号化して元に戻すのではなく、入力と保存ハッシュが一致するかを検査する方式。
- 既存の平文保存データとの互換処理が残っており、通常ログイン成功時に旧形式をハッシュへ移行する。
- 平文互換は既存データの移行措置であり、安全な新規保存方式として使うものではない。
- プロフィールの確認画面にパスワードをhiddenで埋めず、タブのセッションへ一時保存する。
- 確定時には対象IDとの対応を確認して取り出し、一時値を削除する。確認用の平文がサーバーセッション内に一時的に存在する点は区別する。

### 3.3 タブ別セッション

担当: [TabSessionFilter](../src/main/java/jp/co/sss/pr/login_function/TabSessionFilter.java)、[tab-session.js](../src/main/resources/static/js/tab-session.js)

通常のCookieだけでは同じブラウザーの複数タブが同じセッションを共有する。
PROSTAではCookieセッションの中にタブごとの論理セッションを設け、サーバーの`request.getSession()`をそのタブ用に差し替える。

- `_tab`のクエリー/フォーム値、または`X-Prosta-Tab`ヘッダーでタブを識別する。
- タブIDはUUID形式。同じ要求内で値が重複・矛盾している場合は拒否する。
- タブIDは認証情報そのものではない。対応するCookieセッションも必要。
- `sessionStorage`と`BroadcastChannel`を使い、複製タブが同じIDを使っていないか確認する。
- HTML画面GETには単回の`_nav`チケットを使い、複製判定前にテスト開始等を実行しない。
- 同一タブの要求を`synchronized`で直列化し、採点の同時送信を重ねて処理しない。
- ログイン成功時は論理セッションIDを変更し、前の解答・確認用パスワード等を引き継がない。
- ログアウトはそのタブの論理セッションを無効化する。他のタブの別ユーザーまではログアウトさせない。
- セッションはプロセスメモリーに依存する。複数サーバー間でそのまま共有できる仕組みではない。

### 3.4 同一アカウントの同時ログイン

担当: [SingleLoginFilter](../src/main/java/jp/co/sss/pr/login_function/SingleLoginFilter.java)、[LoginController](../src/main/java/jp/co/sss/pr/login_function/LoginController.java)

> 「タブを分ける仕組み」と「同じ人は最後のログインだけを有効にする仕組み」は別の役割。

1. ログイン成功時に新しいトークンを生成し、`customer.active_login_token`へ保存する。
2. 同じトークンをサーバー側の論理セッションにも保持する。DBログイントークンはHTML/URLへ出さない。
3. 認証済み要求では、顧客行の悲観ロックを取り、DBとセッションのトークンを照合する。
4. 一致しない要求は失効とし、画面はログインエラーへ、APIは401と失効ヘッダーを返す。
5. 照合から処理・コミットまでロックを保持することで、「確認だけ通って、失効後に書き込む」隙間を作らない。

ロック待ちの間に別の要求が確定した可能性があるため、取得済みEntityも`refresh`して最新値を確認する。
古いセッションのログアウトが、新しいログインのDBトークンを消さないよう、ログアウトも同じ制御下に置く。

### 3.5 認証・権限・所有権

担当: [LoginCheck](../src/main/java/jp/co/sss/pr/login_function/LoginCheck.java)、[AccessPolicy](../src/main/java/jp/co/sss/pr/login_function/AccessPolicy.java)

- 公開URL以外はログインが必要。未ログインはフィルター段階でログインエラーへリダイレクトされる場合がある。
- `/admin/`、ユーザー一覧・削除・復元等は管理者権限が必要。
- 一般ユーザーのプロフィール更新は自分だけ。対象IDを送信し直してもサーバーで確認する。
- 学習予定は「予定ID＋ログイン中の所有者」で取得し、他人の予定IDだけを渡して変更できないようにする。
- フレンドAPIは一般ユーザーを対象とし、申請の当事者・送受信方向・状態を確認する。
- 画面でボタンを隠す処理は補助。権限確認の本体はサーバー側。

### 3.6 送信元・出力・Cookie・戻り先

| 対策 | 実装・目的 | 範囲・注意 |
|---|---|---|
| 更新要求の送信元確認 | POST/PUT/PATCH/DELETEでOrigin、なければRefererのHostを比較 | 両方ない要求は許可する。schemeまで厳密な同一オリジン比較やCSRFトークン方式ではない |
| 戻り先許可リスト | [ReturnUrls](../src/main/java/jp/co/sss/pr/service/ReturnUrls.java)で既知の画面だけを採用 | 任意の外部URLへ戻さない。入力値を無条件にredirectへ連結しない |
| 文字列として表示 | Thymeleafの`th:text`、JSの`textContent`を利用 | HTML挿入を避ける設計。全箇所を網羅した脆弱性監査の保証ではない |
| レスポンスヘッダー | nosniff / SAMEORIGIN / same-originのReferrer-Policy | MIME推測・外部フレーム・Referer送信の抑制 |
| 動的画面のキャッシュ抑制 | タブフィルターで`Cache-Control: no-store` | 戻る操作等もJS側で再検証する。すべてのブラウザー内部状態を消す意味ではない |
| Cookie | 共通でHttpOnly、SameSite=Lax | CookieのJSからの読取りやクロスサイト送信を制限。これ単独で全CSRF対策にはならない |
| 本番HTTPS | oracleだけforward headersを処理しSecure Cookieを指定 | 証明書・Apache/LB・外部Tomcat設定は別途必要 |

認証関連のID、パスワード、接続情報を説明・障害調査用ログへ安易に出力しない。

## 4. DB整合性と今回の500エラー修正

### 4.1 コミット後のセッション反映

担当: [AfterCommit](../src/main/java/jp/co/sss/pr/service/AfterCommit.java)

DB保存前に「採点完了」「ログイン成功」としてセッションを変えると、DBだけ失敗した際に画面とDBが矛盾する。
そのため、対応するDB保存が確定してから結果・認証情報を公開する。
採点時も、確定するまで解答途中の状態を残し、ロールバック時に途中状態だけが消えることを避ける。

フィルター側でコミットする時点ではリクエストの文脈が外れている場合がある。
`AfterCommit`は登録時のRequestAttributesを一時的に再設定し、処理後は元に戻す。

### 4.2 行ロックとDynamicUpdateの違い

- 行ロック: 同じ顧客のEXP加算やログイン切替を順序付ける。
- `@DynamicUpdate`: Entityの変更列だけをUPDATEし、heartbeatが未変更のEXP等を上書きしない。
- DynamicUpdateだけで同時加算の欠落を防げるわけではない。両方を別目的で使う。

### 4.3 解除後フィードの404が500へ変わる問題

担当: [FriendFeedController](../src/main/java/jp/co/sss/pr/mypage_function/FriendFeedController.java)

修正前:

```text
フレンド解除済み
 -> フィードでResponseStatusException(404)
 -> 内側の@Transactionalが共有トランザクションをrollback-onlyにする
 -> MVCは404として解決するが、外側のフィルターが確定しようとする
 -> UnexpectedRollbackException -> HTTP500
```

修正:

```java
@Transactional(readOnly = true, noRollbackFor = ResponseStatusException.class)
```

読み取り専用のフィード取得だけで、想定内のHTTPエラーをロールバック指定から除外する。
DB接続障害など別の実行時例外は引き続きロールバック対象。
この指定は「常にコミットを強制する」という意味ではなく、他で既にrollback-onlyになった状態を解除するものでもない。

**注意:** 更新APIへ一括でこの指定を付けない。途中更新を残さないかの検討が必要。
追加検証で別APIにも同じ問題を確認したため、次節の共有境界でのロールバック処理を追加した。

### 4.4 他の400・403・404・409を500へ変えない

担当: [SingleLoginFilter](../src/main/java/jp/co/sss/pr/login_function/SingleLoginFilter.java)

フレンド申請・背景変更・ユーザー更新/削除でも、MVCが想定内の4xxへ解決した後、
外側の確定時にUnexpectedRollbackExceptionとなるケースが追加テストで40件見つかった。

共有トランザクション内の下流処理から戻った時点で、応答が400以上500未満なら
`status.setRollbackOnly()`を呼ぶ。外側でも明示的にロールバックを選ぶことで、
内側のrollback-onlyをコミットしようとして500になることを避ける。

- 4xx要求の途中変更は保存しない。ロールバック指定を解除したりコミットを強制したりしない。
- AfterCommitに登録した処理も実行しない。
- 成功応答のコミット、顧客行ロック、ログイントークン照合は維持する。
- DB障害などの例外をcatchして成功扱いにしない。通常どおり伝播・ロールバックする。
- 対象はHTTPの4xx応答。200の入力エラー画面やリダイレクトを自動的にエラー判定する処理ではない。
- フィード単体の読取専用例外設定は維持するが、フィルターを通る4xx要求は共有境界でロールバックする。

フレンド32ケース・背景/ユーザー更新/カレンダー等20ケースのフィルター込みテスト、
実HTTPでの400/403/404/409と後続要求、
途中書込み・AfterCommit抑止・DB障害・正常コミットのテストを追加した。

## 5. 学習機能のロジック

### 5.1 出題と採点

担当: [TestController](../src/main/java/jp/co/sss/pr/test_function/TestController.java)

- カテゴリ別: 指定カテゴリ・難易度からランダムに最大15問。
- 苦手範囲特定: 3カテゴリ以上を選択し、カテゴリごとの問題を順に取り出して偏りを減らす。
- 弱点問題: 後述の問題別正答率から対象を選ぶ。
- 復習: 各問題の最後の解答が不正解だったものを対象にする。
- 出題・途中解答はタブセッションに保持。解答→確認→採点→結果GETという流れ。
- 解答1件をAnswerへ保存し、正解数・満点回数・EXP・実績を同じトランザクションで更新する。
- 結果はPOST後にGETへリダイレクトする（PRG）。同一タブ直列化と途中状態の破棄も併用して二重採点を抑止する。
- 結果のキャラクターは正答率で変え、レベルアップ時は専用画像・メッセージを優先する。

採点・タイマーについて、入力値の改ざんや厳密なサーバー側期限強制まで対策済みと一括して説明しない。
現在の採点は確認時に保存したAnswerFormの値を利用する構造であり、DB正解の再照合等は別途確認する観点。

### 5.2 タイマー

担当: [timer.html](../src/main/resources/templates/common/timer.html)

- 任意のタイマー付き出題は1問25秒。開始時刻と制限時間をサーバーのセッションに保存する。
- 各画面へ残時間を渡し、JSが画面読込後の実経過時間を引いて表示する。
- `setInterval`の回数で減算しないため、非表示タブでコールバックが遅れても経過時間を反映できる。
- 解答画面の時間切れは`/test/timeup`へ送信。不明・未選択を「わからない」に補正して採点へ進む。
- 通常の`form.submit()`はsubmitイベントを発火しないため、タブJSでも別途ラップしてIDを付ける。
- JSの自動送信は利便性の機能であり、ブラウザーの時計・JS変更への防御を保証するものではない。

### 5.3 弱点と復習は異なる

担当: [WeakQuestionService](../src/main/java/jp/co/sss/pr/service/WeakQuestionService.java)

| 機能 | 判断基準 |
|---|---|
| 弱点問題 | 同じ問題を2回以上解いた履歴を集計し、全問正解の問題を除外。正答率が低い順、同率なら解答回数が多い順等で最大15問 |
| 復習モード | 解答IDの新しい順に見て、各問題を一度だけ判定。最後に正解した問題は古い誤答があっても対象外 |
| 学習状況の弱点表示 | カテゴリ単位。解答あり、丸めた正答率60%未満を弱点として表示 |

「問題別の弱点」と「カテゴリ別の弱点」は異なる集計なので、対象数が一致するとは限らない。

### 5.4 EXP・レベル・実績・クエスト

担当: [LevelService](../src/main/java/jp/co/sss/pr/service/LevelService.java)、[QuestService](../src/main/java/jp/co/sss/pr/service/QuestService.java)

```text
今回の獲得EXP = 正解数 × 2 + 満点の場合のみ5
レベル = floor(total_exp / 15) + 1
レベル内進捗 = total_exp % 15
次のレベルまで = 15 - レベル内進捗
```

- 同日2回目以降のログインではログイン日数を増やさない。前日との差から連続ログイン日数を更新する。
- ログインでEXPは加算しない。保存済みtotal_expを正とし、過去の履歴から毎回作り直さない。
- 満点回数は「同じ日の全問正解」ではなく、テスト単位で加算する。
- 実績はログイン日数、レベル、正解数、満点回数等を判定し、解除済みの記録は重ねて登録しない。
- 今日のクエストは5問解答・3問正解・5問以上かつ正答率80%以上。
- クエスト専用の達成フラグを保存せず、当日の履歴から都度計算する。正答率は表示と同じ丸め値を使う。
- キャラの表示段階はLv1/10/25/50/75/100。画像の段階とレベル上限は別概念。

## 6. MyPage・管理・フレンド

| 機能 | 実装の要点 |
|---|---|
| MyPage | DBのレベル、累計正解・満点回数、実績、当日クエストを組み合わせて表示 |
| 解答履歴 | 本人の履歴をカテゴリ・難易度・問題文・正誤・期間で絞り込み、DB側で1ページ6件。誤答回数は本人の全履歴を基準に問題別集計 |
| 学習状況 | カテゴリ別の解答数・正解数・正答率と、最近15件の解答を表示。未解答カテゴリも一覧化 |
| 学習カレンダー | 月内の日別集計と予定件数を対応付け、月曜始まりの7列に配置。必要な週数を計算して月外セルも含める |
| 学習予定 | タイトル100文字・詳細500文字の制限。更新/削除は所有者条件付き検索。保存後は対象日へリダイレクト |
| 背景 | 既知の背景名と必要レベルをサーバーで検査。任意色は`#RRGGBB`だけを受け付ける |
| 背景NEW | 前回確認レベルと現在レベルの間で新規解放された背景数を計算 |
| 問題検索 | カテゴリ・難易度・問題文で検索し、問題内容を確認 |
| 管理者の問題管理 | カテゴリ/難易度/文言/解説なしで絞込み。DB側で1ページ10件。入力検査後に保存し、DB整合性エラーは画面に通知 |
| ユーザー管理 | 管理者用の一覧・更新・削除/復元。一般ユーザーの入口とはアクセス権を分ける |
| ログアウト前サマリー | 当日の解答数・正解数・正答率と、累計・弱いカテゴリを集計。サマリー表示と実ログアウトは別処理 |

### 6.1 フレンド申請・比較

担当: [FriendController](../src/main/java/jp/co/sss/pr/mypage_function/FriendController.java)

- 関係の2人を小さいID/大きいIDへ正規化して保存し、組合せの一意制約で方向違いの二重レコードを避ける。
- `PENDING`から受信者が承認すると`ACCEPTED`。拒否は`REJECTED`。送信者は保留中の申請を取り消せる。
- 検索対象は削除されていない一般ユーザー。本人を除き、最大20件。
- オンラインは最終確認時刻が直近5分以内かで判定する。実際に画面を見ている保証ではない。
- ランキングの対象は本人と承認済みフレンド。全ユーザーランキングではない。
- カテゴリ・難易度・期間で比較し、正答率、正解数、解答数、名前の順に並べる。未来日・逆転期間・許容範囲外の期間を拒否する。
- APIの一覧・比較はまとめて学習集計を取得し、表示専用recordを返す。

### 6.2 フレンドフィード

担当: [FriendFeedController](../src/main/java/jp/co/sss/pr/mypage_function/FriendFeedController.java)、[フレンド画面](../src/main/resources/templates/friends/index.html)

- 一般ユーザー同士で承認済み・削除されていない場合のみ取得可能。
- 今日を含む30日間の「日別解答数・正解数」と「実績獲得」を日付の新しい順に返す。
- 正確な記録のない過去のレベルアップ日時や、テスト単位の満点は生成しない。
- 日付はJSON文字列として返す。フロントで数値配列の日付を解釈する必要をなくす。
- モーダル上部のレベル・キャラはフレンド一覧取得時の情報。開いた瞬間の最新レベルを別取得する仕様ではない。
- リクエスト番号を比較し、閉じた後や別フレンドを開いた後の古い応答で内容を上書きしない。
- 読込中・活動なし・取得失敗を区別して表示する。
- Escape/背景/閉じるで終了し、ボタンへフォーカスを戻す。定期再描画で元のボタンが消えた場合も考慮する。
- 現状のモーダル内の操作要素は閉じるボタンだけ。リンク等を増やすときはフォーカス循環も変更する。

### 6.3 チャット

担当: [ChatService](../src/main/java/jp/co/sss/pr/service/ChatService.java)、[chatbot.js](../src/main/resources/static/js/chatbot.js)

外部の生成AIへ送信せず、入力のキーワードを上から順に判定して、本人の学習集計・保存済みの解説・画面リンクを返す。
「出題」「弱点」「成績」等の判定順で応答が決まるため、似た語のルール追加時は順序に注意する。
自由な質問に必ず答えられるAIではない。画面側はメッセージをtextContentで表示し、通信失敗も通知する。

CSSは後勝ちだけでなく、詳細度・継承・media条件にも左右される。既存の共通指定を広く変えると別画面へ波及する。

### 7.2 PCと狭い画面

- 主な切替は1184px以下／1185px以上。600px以下等の追加調整もある。

「スマホ対応」は物理機種名ではなくCSS幅で切り替わる。横向き・拡大・長い文字・ソフトキーボードも別途検査する。
横はみ出しがないだけで、文字の読みやすさ・重なり・ボタンの押しやすさまで保証されるわけではない。

### 8.1 ページ分割は2種類

- クライアント方式: 取得済み行を非表示にする。解答をDOMから削除しないので、別ページの入力もフォームに保持できる。
- サーバー方式: RepositoryのPageableで取得件数を区切る。選択したページのURLへ移動する。

どちらも「前へ/次へ/ページ選択」に見えるが、通信・データ量・入力保持が異なる。
クライアント方式は全件取得量を減らす仕組みではない。

### 8.2 非同期通信

- fetchのHTTPエラーは自動で例外にならないため、`response.ok`やstatusを確認する。
- フレンド更新の204は本文なし。無条件でJSONとして読むとエラーになるため分岐する。
- 同時ログイン失効の401＋専用ヘッダーは、共通fetchラッパーからログインエラーへ誘導する。
- DOMを毎回再生成する箇所では、古い要素参照・イベント登録・フォーカス位置にも注意する。
- タブJSの初期化完了前にはフォーム/APIを待たせる。bfcacheから戻ったページも再読込みで状態を検証する。
- 外部ライブラリーの圧縮済みコードは説明コメントの追記対象とせず、独自実装側に意図を書く。

## 12. よく聞かれる質問への短い答え

- **なぜサーバーでチェックする？** ブラウザー側の非表示・入力制限は書き換えられるため、権限・所有者・形式はサーバーでも確認します。
- **なぜDBトークンとタブIDが両方ある？** タブIDは同じブラウザー内の状態分離、DBトークンは同じアカウントの古いログインの失効です。
- **なぜ行ロックする？** 照合と書込みを一続きにし、並行要求による古い認証の書込みやEXP加算の欠落を避けるためです。
- **なぜコミット後に結果を出す？** DB保存に失敗したのに、セッションだけ成功状態になることを避けるためです。
- **なぜ4xxが500にならなくなった？** 最初は読取専用フィードへ限定した例外設定で修正しました。追加検証後は共有フィルターでも4xxを明示的にロールバックし、本来のHTTPステータスと更新の取り消しを両立しています。DB障害も引き続きロールバックします。
- **なぜCSSを分ける？** 全体配置・共通部品・画面固有を分け、変更の影響範囲を追いやすくするためです。ただし読込順と詳細度の影響は残ります。
- **AIチャットなの？** 現状は外部生成AIではなく、キーワードと自分のデータによるルールベースです。
