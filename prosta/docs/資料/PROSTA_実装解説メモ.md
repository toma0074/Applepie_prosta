# PROSTA 実装解説メモ

更新日: 2026-11-02

機能、認証・データ保護、JavaScript、CSSの「どう実装しているか」「なぜその方式か」を説明するための資料。
第13章以降は、現行ソースから確認した処理順・条件・計算例・保存範囲を補足した詳細ロジック編。
ソースを確認した時点の実装を記載する。対策が存在することと、あらゆる不正・障害を防げることは区別する。
作業の時系列は [作業ログ](./作業ログ.md)、本番のHTTPS構築は [HTTPS設定手順](../configuration/OCI_Apache_Tomcat_HTTPS設定手順.md) を参照。

## 1. 最初に説明するなら

> PROSTAは、Java/Spring Bootで処理し、ThymeleafでHTMLを生成する学習アプリです。
> 問題・解答履歴・ユーザー情報をDBへ保存し、履歴の集計から弱点、学習状況、実績などを表示します。
> JavaScriptは非同期API通信やモーダル、タイマーなどを担当し、CSSでPCと狭い画面の配置を切り替えます。
> 認証ではタブ別のセッション分離とDB上のログイントークンを組み合わせ、別ユーザーの混同と同一アカウントの古いログインからの更新を防ぎます。

## 2. 全体構成と処理の流れ

### 2.1 主な技術

- Java 17 / Spring Boot 3.1.5 / Spring MVC
- Thymeleaf: HTMLテンプレートへの値の埋め込み、共通部品の再利用
- Spring Data JPA / Hibernate: DBアクセス、Entityの変更保存、トランザクション
- Oracle: 本番の永続データ。今回の自動検証ではH2へ差し替えている
- JavaScript: 標準DOM API / fetch中心。一部はHTML内のインラインスクリプト
- JUnit / MockMvc: ロジック、API、画面テンプレート、認証フィルター込みの回帰テスト

### 2.2 1リクエストの流れ

```text
ブラウザーのリンク・フォーム・fetch
  -> タブIDの付与
  -> TabSessionFilter: タブのHttpSessionへ差替え、同一タブを直列処理
  -> LoginCheck: 公開URL・ログイン・管理者権限・送信元の確認
  -> SingleLoginFilter: 顧客行ロック、現在のログイントークンの照合
  -> Controller: 入力確認、対象の所有権確認、Service/Repository呼出し
  -> Service / Repository / Entity: 業務処理、DB検索・保存
  -> HTML描画またはJSON/リダイレクト
  -> DBトランザクション確定、必要に応じてAfterCommit処理
```

静的ファイル、公開URL、未ログインの要求は、各フィルターの除外条件に従う。
すべてのリクエストが必ず顧客行ロックを取るわけではない。

### 2.3 パッケージの役割

基準: [Javaソース](../../src/main/java/jp/co/sss/pr)

| 場所 | 役割 |
|---|---|
| `login_function` | ログイン・登録・ログアウト、タブ分離、アクセス制御、heartbeat |
| `mypage_function` | MyPage、履歴、学習状況、予定、フレンド、背景、実績、チャットの入口 |
| `test_function` | 出題選択、解答、確認、採点、結果表示 |
| `question_function` | 問題検索、管理者向け問題管理 |
| `user_function` | ユーザー更新、管理者のユーザー管理 |
| `service` | EXP・弱点・クエスト・チャット等の業務ロジック |
| `repository` | DB検索、ページ分割、件数・日別・カテゴリ別集計 |
| `entity` | テーブルとJavaオブジェクトの対応 |
| `form` / `bean` | 画面入力の受け取り、表示・セッション用データ |

Entityをそのまま全項目JSON化するのではなく、フレンドAPI等では必要な項目だけのrecordへ変換する。

## 3. 登録・認証・セキュリティ関連の実装

### 3.1 登録とユーザー名の重複

担当: [LoginController](../../src/main/java/jp/co/sss/pr/login_function/LoginController.java)、[UserController](../../src/main/java/jp/co/sss/pr/user_function/UserController.java)、[CustomerForm](../../src/main/java/jp/co/sss/pr/form/CustomerForm.java)

- 新規登録: `existsByUserName`で同名の存在を確認する。
- 更新: `existsByUserNameAndUserIdNot`で本人以外との重複を確認する。名前を変えない更新は許可する。
- 更新確認時だけでなく確定時にも確認する。他の操作で状態が変わった可能性があるため。
- 現在のフォーム制限はユーザー名1～8文字、パスワード4～16文字の英数字。DBの名前列の長さ20とは別の制約。
- 論理削除ユーザーを除外した重複確認ではないため、削除済みの名前も使用済みとして扱う。
- 存在確認はアプリ側の検査であり、同時登録の原子的な一意性をそれだけで保証するものではない。DBの一意制約や並行要求については別の観点で確認する。

### 3.2 パスワード

担当: [PasswordService](../../src/main/java/jp/co/sss/pr/service/PasswordService.java)

- 新規保存・更新はBCryptでハッシュ化し、照合はBCryptPasswordEncoderを使う。
- 暗号化して元に戻すのではなく、入力と保存ハッシュが一致するかを検査する方式。
- 既存の平文保存データとの互換処理が残っており、通常ログイン成功時に旧形式をハッシュへ移行する。
- 平文互換は既存データの移行措置であり、安全な新規保存方式として使うものではない。
- プロフィールの確認画面にパスワードをhiddenで埋めず、タブのセッションへ一時保存する。
- 確定時には対象IDとの対応を確認して取り出し、一時値を削除する。確認用の平文がサーバーセッション内に一時的に存在する点は区別する。

### 3.3 タブ別セッション

担当: [TabSessionFilter](../../src/main/java/jp/co/sss/pr/login_function/TabSessionFilter.java)、[tab-session.js](../../src/main/resources/static/js/tab-session.js)

通常のCookieだけでは同じブラウザーの複数タブが同じセッションを共有する。
PROSTAではCookieセッションの中にタブごとの論理セッションを設け、サーバーの`request.getSession()`をそのタブ用に差し替える。

- `_tab`のクエリー/フォーム値、または`X-Prosta-Tab`ヘッダーでタブを識別する。
- タブIDはUUID形式。同じ要求内で値が重複・矛盾している場合は拒否する。
- タブIDは認証情報そのものではない。対応するCookieセッションも必要。
- `sessionStorage`と`BroadcastChannel`を使い、複製タブが同じIDを使っていないか確認する。
- HTML画面GETには単回の`_nav`チケットを使い、複製判定前にテスト開始等を実行しない。
- 同一タブの要求を`synchronized`で直列化し、採点の同時送信を重ねて処理しない。
- ログイン成功時は論理セッションIDを変更し、前の解答・確認用パスワード等を引き継がない。
- ログアウトはそのタブの論理セッションを無効化する。他のタブの別ユーザーまではログアウトさせない。
- セッションはプロセスメモリーに依存する。複数サーバー間でそのまま共有できる仕組みではない。

### 3.4 同一アカウントの同時ログイン

担当: [SingleLoginFilter](../../src/main/java/jp/co/sss/pr/login_function/SingleLoginFilter.java)、[LoginController](../../src/main/java/jp/co/sss/pr/login_function/LoginController.java)

> 「タブを分ける仕組み」と「同じ人は最後のログインだけを有効にする仕組み」は別の役割。

1. ログイン成功時に新しいトークンを生成し、`customer.active_login_token`へ保存する。
2. 同じトークンをサーバー側の論理セッションにも保持する。DBログイントークンはHTML/URLへ出さない。
3. 認証済み要求では、顧客行の悲観ロックを取り、DBとセッションのトークンを照合する。
4. 一致しない要求は失効とし、画面はログインエラーへ、APIは401と失効ヘッダーを返す。
5. 照合から処理・コミットまでロックを保持することで、「確認だけ通って、失効後に書き込む」隙間を作らない。

ロック待ちの間に別の要求が確定した可能性があるため、取得済みEntityも`refresh`して最新値を確認する。
古いセッションのログアウトが、新しいログインのDBトークンを消さないよう、ログアウトも同じ制御下に置く。

### 3.5 認証・権限・所有権

- 放置などでセッションが切れた場合、通常画面はログイン案内へ転送し、APIは401と`X-Prosta-Login-Expired`を返す。共通のfetch処理が同じタブのログイン案内へ遷移するため、ログイン画面のHTMLをJSONとして読み込まない。
- フレンド画面では応答のContent-Typeも確認し、想定外のHTMLやJSON解析エラーを技術的な文言のまま画面へ表示しない。

担当: [LoginCheck](../../src/main/java/jp/co/sss/pr/login_function/LoginCheck.java)、[AccessPolicy](../../src/main/java/jp/co/sss/pr/login_function/AccessPolicy.java)

- 公開URL以外はログインが必要。未ログインはフィルター段階でログインエラーへリダイレクトされる場合がある。
- `/admin/`、ユーザー一覧・削除・復元等は管理者権限が必要。
- 一般ユーザーのプロフィール更新は自分だけ。対象IDを送信し直してもサーバーで確認する。
- 学習予定は「予定ID＋ログイン中の所有者」で取得し、他人の予定IDだけを渡して変更できないようにする。
- フレンドAPIは一般ユーザーを対象とし、申請の当事者・送受信方向・状態を確認する。
- 画面でボタンを隠す処理は補助。権限確認の本体はサーバー側。

### 3.6 送信元・出力・Cookie・戻り先

| 対策 | 実装・目的 | 範囲・注意 |
|---|---|---|
| 更新要求の送信元確認 | POST/PUT/PATCH/DELETEでOrigin、なければRefererのHostを比較 | 両方ない要求は許可する。schemeまで厳密な同一オリジン比較やCSRFトークン方式ではない |
| 戻り先許可リスト | [ReturnUrls](../../src/main/java/jp/co/sss/pr/service/ReturnUrls.java)で既知の画面だけを採用 | 任意の外部URLへ戻さない。入力値を無条件にredirectへ連結しない |
| 文字列として表示 | Thymeleafの`th:text`、JSの`textContent`を利用 | HTML挿入を避ける設計。全箇所を網羅した脆弱性監査の保証ではない |
| レスポンスヘッダー | nosniff / SAMEORIGIN / same-originのReferrer-Policy | MIME推測・外部フレーム・Referer送信の抑制 |
| 動的画面のキャッシュ抑制 | タブフィルターで`Cache-Control: no-store` | 戻る操作等もJS側で再検証する。すべてのブラウザー内部状態を消す意味ではない |
| Cookie | 共通でHttpOnly、SameSite=Lax | CookieのJSからの読取りやクロスサイト送信を制限。これ単独で全CSRF対策にはならない |
| 本番HTTPS | oracleだけforward headersを処理しSecure Cookieを指定 | 証明書・Apache/LB・外部Tomcat設定は別途必要 |

認証関連のID、パスワード、接続情報を説明・障害調査用ログへ安易に出力しない。

## 4. DB整合性と今回の500エラー修正

### 4.1 コミット後のセッション反映

担当: [AfterCommit](../../src/main/java/jp/co/sss/pr/service/AfterCommit.java)

DB保存前に「採点完了」「ログイン成功」としてセッションを変えると、DBだけ失敗した際に画面とDBが矛盾する。
そのため、対応するDB保存が確定してから結果・認証情報を公開する。
採点時も、確定するまで解答途中の状態を残し、ロールバック時に途中状態だけが消えることを避ける。

フィルター側でコミットする時点ではリクエストの文脈が外れている場合がある。
`AfterCommit`は登録時のRequestAttributesを一時的に再設定し、処理後は元に戻す。

### 4.2 行ロックとDynamicUpdateの違い

- 行ロック: 同じ顧客のEXP加算やログイン切替を順序付ける。
- `@DynamicUpdate`: Entityの変更列だけをUPDATEし、heartbeatが未変更のEXP等を上書きしない。
- DynamicUpdateだけで同時加算の欠落を防げるわけではない。両方を別目的で使う。

### 4.3 解除後フィードの404が500へ変わる問題

担当: [FriendFeedController](../../src/main/java/jp/co/sss/pr/mypage_function/FriendFeedController.java)

修正前:

```text
フレンド解除済み
 -> フィードでResponseStatusException(404)
 -> 内側の@Transactionalが共有トランザクションをrollback-onlyにする
 -> MVCは404として解決するが、外側のフィルターが確定しようとする
 -> UnexpectedRollbackException -> HTTP500
```

修正:

```java
@Transactional(readOnly = true, noRollbackFor = ResponseStatusException.class)
```

読み取り専用のフィード取得だけで、想定内のHTTPエラーをロールバック指定から除外する。
DB接続障害など別の実行時例外は引き続きロールバック対象。
この指定は「常にコミットを強制する」という意味ではなく、他で既にrollback-onlyになった状態を解除するものでもない。

**注意:** 更新APIへ一括でこの指定を付けない。途中更新を残さないかの検討が必要。
追加検証で別APIにも同じ問題を確認したため、次節の共有境界でのロールバック処理を追加した。

### 4.4 他の400・403・404・409を500へ変えない

担当: [SingleLoginFilter](../../src/main/java/jp/co/sss/pr/login_function/SingleLoginFilter.java)

フレンド申請・背景変更・ユーザー更新/削除でも、MVCが想定内の4xxへ解決した後、
外側の確定時にUnexpectedRollbackExceptionとなるケースが追加テストで40件見つかった。

共有トランザクション内の下流処理から戻った時点で、応答が400以上500未満なら
`status.setRollbackOnly()`を呼ぶ。外側でも明示的にロールバックを選ぶことで、
内側のrollback-onlyをコミットしようとして500になることを避ける。

- 4xx要求の途中変更は保存しない。ロールバック指定を解除したりコミットを強制したりしない。
- AfterCommitに登録した処理も実行しない。
- 成功応答のコミット、顧客行ロック、ログイントークン照合は維持する。
- DB障害などの例外をcatchして成功扱いにしない。通常どおり伝播・ロールバックする。
- 対象はHTTPの4xx応答。200の入力エラー画面やリダイレクトを自動的にエラー判定する処理ではない。
- フィード単体の読取専用例外設定は維持するが、フィルターを通る4xx要求は共有境界でロールバックする。

フレンド32ケース・背景/ユーザー更新/カレンダー等20ケースのフィルター込みテスト、
実HTTPでの400/403/404/409と後続要求、
途中書込み・AfterCommit抑止・DB障害・正常コミットのテストを追加した。

## 5. 学習機能のロジック

### 5.1 出題と採点

担当: [TestController](../../src/main/java/jp/co/sss/pr/test_function/TestController.java)

- カテゴリ別: 指定カテゴリ・難易度からランダムに出題。各出題モードで5/10/15問を選べ、対象問題が少なければその件数まで出題する。
- 苦手範囲特定: 3カテゴリ以上を選択し、カテゴリごとの問題を順に取り出して偏りを減らす。
- 弱点問題: 後述の問題別正答率から対象を選ぶ。
- 復習: 各問題の最後の解答が不正解だったものを対象にする。
- 出題・途中解答はタブセッションに保持。解答→確認→採点→結果GETという流れ。
- 解答1件をAnswerへ保存し、正解数・満点回数・EXP・実績を同じトランザクションで更新する。
- 結果はPOST後にGETへリダイレクトする（PRG）。同一タブ直列化と途中状態の破棄も併用して二重採点を抑止する。
- 結果のキャラクターは正答率で変え、レベルアップ時は専用画像・メッセージを優先する。
- 結果には選択した解答・正解・解説・前回の解答を並べ、ブックマークの切替と学習メモ・報告への入口を設ける。

[AnswerGradingService](../../src/main/java/jp/co/sss/pr/service/AnswerGradingService.java)が、出題済みIDと順序・件数・解答値を検査し、正解・問題文・カテゴリ・解説をDBから再取得する。ブラウザーが送信した正解値は採点に使わず、解答画面にも正解をhiddenで埋めない。これは厳密なサーバー側タイマー期限強制とは別の対策。

### 5.2 タイマー

担当: [timer.html](../../src/main/resources/templates/common/timer.html)

- 任意のタイマー付き出題は1問25秒。開始時刻と制限時間をサーバーのセッションに保存する。
- 各画面へ残時間を渡し、JSが画面読込後の実経過時間を引いて表示する。
- `setInterval`の回数で減算しないため、非表示タブでコールバックが遅れても経過時間を反映できる。
- 解答画面の時間切れは`/test/timeup`へ送信。不明・未選択を「わからない」に補正して採点へ進む。
- 通常の`form.submit()`はsubmitイベントを発火しないため、タブJSでも別途ラップしてIDを付ける。
- JSの自動送信は利便性の機能であり、ブラウザーの時計・JS変更への防御を保証するものではない。

### 5.3 弱点と復習は異なる

担当: [WeakQuestionService](../../src/main/java/jp/co/sss/pr/service/WeakQuestionService.java)

| 機能 | 判断基準 |
|---|---|
| 弱点問題 | 同じ問題を2回以上解いた履歴を集計し、全問正解の問題を除外。正答率が低い順、同率なら解答回数が多い順等で最大15問 |
| 復習モード | 解答IDの新しい順に見て、各問題を一度だけ判定。最後に正解した問題は古い誤答があっても対象外 |
| 間隔を空けた復習 | 最後の解答日と別日に連続して正解した回数から復習日を計算。誤答は翌日、連続正解は1/3/7/14/30日後。同日中の反復だけでは間隔を延ばさない |
| 学習状況の弱点表示 | カテゴリ単位。解答あり、丸めた正答率60%未満を弱点として表示 |

「問題別の弱点」と「カテゴリ別の弱点」は異なる集計なので、対象数が一致するとは限らない。

「今日のおすすめ学習」は、期限の来た復習、直近の誤答、問題別の弱点、未学習カテゴリ、登録済みの学習可能なカテゴリの順で提案するルールベース機能。マイページにはおすすめ学習・今日の復習のタイルを表示せず、各学習画面への既存の入口は維持する。復習予定は本人の解答履歴から算出するため専用テーブルは不要。

### 5.4 EXP・レベル・実績・クエスト

- 当日の3つのクエストをすべて達成すると、解答の採点時に通常のEXPに加えて10 EXPを自動付与する（1ユーザーにつき1日1回）。
- customer.quest_reward_dateに付与日を記録し、再解答・再ログイン・再読み込みで重複加算しない。報酬によるレベルアップ・実績解除も同じ採点処理で判定する。
- 必要な列・表・制約は[現状最新.sql](../db/現状最新.sql)に含む。直前バックアップ後に再構築する運用へ統一し、増分SQLは廃止した。再構築では既存データを削除するため、最新バックアップとのデータ差分を確認してから実行する。

担当: [LevelService](../../src/main/java/jp/co/sss/pr/service/LevelService.java)、[QuestService](../../src/main/java/jp/co/sss/pr/service/QuestService.java)

```text
今回の獲得EXP = 正解数 × 2 + 満点の場合のみ5
             + 当日の全クエスト達成報酬10（未付与の場合のみ）
レベル = floor(total_exp / 15) + 1
レベル内進捗 = total_exp % 15
次のレベルまで = 15 - レベル内進捗
```

- 同日2回目以降のログインではログイン日数を増やさない。前日との差から連続ログイン日数を更新する。
- ログインでEXPは加算しない。保存済みtotal_expを正とし、過去の履歴から毎回作り直さない。
- 満点回数は「同じ日の全問正解」ではなく、テスト単位で加算する。
- 実績はログイン日数、レベル、正解数、満点回数等を判定し、解除済みの記録は重ねて登録しない。
- 今日のクエストは5問解答・3問正解・5問以上かつ正答率80%以上。
- 正答率は表示と同じ丸め値を使う。達成したクエストを`quest_progress_date`と`quest_completed_mask`へ保存し、その日の後の誤答で未達成に戻さない。翌日は当日分を改めて計算する。
- 10 EXPを今回獲得した場合は解答結果にも通知する。達成状態・報酬・解答保存は同じトランザクション内で確定する。
- キャラの表示段階はLv1/10/25/50/75/100。画像の段階とレベル上限は別概念。

### 5.5 ブックマーク一覧と出題

- MENUまたは問題検索画面から「ブックマーク一覧」を開き、自分が登録した全件を確認・解除できる。
- 問題一覧・ブックマーク一覧の☆/★ボタンは、登録状態を変更せずにその問題の解説・学習メモ画面へ移動する。登録・解除は詳細画面のブックマークボタンで操作し、操作後も詳細画面に留まる。戻るボタンは元の一覧へ戻す。解答結果のブックマーク操作は従来どおり結果画面へ戻る。
- カテゴリ・難易度で絞り込み、チェックした問題だけから出題できる。チェックなしなら絞り込み後の全件を候補とする。
- 「ブックマークから出題」で、開始時点の対象問題からランダムに5/10/15問まで出題する（初期値15問）。制限時間は設けない。
- 未登録時は案内を表示し、出題ボタンを表示しない。詳細画面で解除した後も詳細画面に留まり、戻るボタンから元の一覧に戻る。
- 出題後は既存の解答・確認・採点処理を利用し、解答履歴・EXP・実績へ反映する。
- 一覧と出題はログインユーザーのIDでDB検索し、他のユーザーの登録問題は含めない。既存のfavoriteテーブルを利用するためSQL変更は不要。

### 6.1 フレンド申請・比較

担当: [FriendController](../../src/main/java/jp/co/sss/pr/mypage_function/FriendController.java)

- 関係の2人を小さいID/大きいIDへ正規化して保存し、組合せの一意制約で方向違いの二重レコードを避ける。
- `PENDING`から受信者が承認すると`ACCEPTED`。拒否は`REJECTED`。送信者は保留中の申請を取り消せる。
- 検索対象は削除されていない一般ユーザー。本人を除き、最大20件。
- オンラインは最終確認時刻が直近5分以内かで判定する。実際に画面を見ている保証ではない。
- ランキングの対象は本人と承認済みフレンド。全ユーザーランキングではない。
- 解答数順/正答率順を切り替え、正解数・解答数の母数も表示する。未解答の正答率は未学習として扱う。

### 6.1.1 非同期フレンド対戦

- `/challenges`から承認済みフレンド、カテゴリ、難易度、5/10/15問を選び、同じ問題セットでそれぞれ都合のよい時間に解答する。
- 出題時の問題文・選択肢・正解・解説・順序を固定して保存する。参加者以外は閲覧・解答できず、解答前に正解を表示しない。
- それぞれ1回だけ提出し、双方の提出後に正解数を比較する。通常の解答履歴・EXP・実績・クエストにも反映する。
- リアルタイム対戦、制限時間競争、別途の勝利EXPは設けない。
- フレンド解除後は新規対戦を作れないが、作成済みの対戦は参加者が引き続き解答・閲覧できる。元問題を削除しても固定問題と対戦結果は残し、削除済み問題の通常解答履歴は作成しない。

### 6.1.2 本人専用メモと問題報告

- 問題検索・ブックマーク一覧・解答結果から問題詳細を開き、解説と本人専用の1000文字以内の学習メモを確認・保存・削除する。
- 空のメモ・文字数超過・報告内容の不備・重複報告は、日本語の案内を表示して入力をやり直せる。DB更新前の利用者向け検証例外は外側の認証トランザクションをrollback-onlyにせず、DB障害は従来どおりロールバックする。
- 正解の誤り/解説が不明瞭/その他の理由で問題を報告できる。その他は詳細入力必須。同じ本人・問題・理由の未対応報告を重ねて送信しない。
- 管理者メニューの「問題・解説の報告」で未対応/対応済み/保留を確認し、対応状況を更新する。一般ユーザーには管理画面を許可しない。
- カテゴリ・難易度・期間で比較し、正答率、正解数、解答数、名前の順に並べる。未来日・逆転期間・許容範囲外の期間を拒否する。
- APIの一覧・比較はまとめて学習集計を取得し、表示専用recordを返す。

### 8.1 ページ分割は2種類

- クライアント方式: 取得済み行を非表示にする。解答をDOMから削除しないので、別ページの入力もフォームに保持できる。
- サーバー方式: RepositoryのPageableで取得件数を区切る。選択したページのURLへ移動する。

どちらも「前へ/次へ/ページ選択」に見えるが、通信・データ量・入力保持が異なる。
クライアント方式は全件取得量を減らす仕組みではない。

### 8.2 非同期通信

- fetchのHTTPエラーは自動で例外にならないため、`response.ok`やstatusを確認する。
- フレンド更新の204は本文なし。無条件でJSONとして読むとエラーになるため分岐する。
- 同時ログイン失効の401＋専用ヘッダーは、共通fetchラッパーからログインエラーへ誘導する。
- DOMを毎回再生成する箇所では、古い要素参照・イベント登録・フォーカス位置にも注意する。
- タブJSの初期化完了前にはフォーム/APIを待たせる。bfcacheから戻ったページも再読込みで状態を検証する。
- 外部ライブラリーの圧縮済みコードは説明コメントの追記対象とせず、独自実装側に意図を書く。

## 9. DB・設定・本番反映

主なテーブル:

- `customer`: 名前・ハッシュ・権限・論理削除、ログイン/EXP/背景/有効ログイントークン
- `category` / `question`: カテゴリ、問題、選択肢、正解、解説
- `answer`: ユーザー・問題・選択結果・正誤・解答日
- `achievement` / `user_achievement`: 実績マスターと解除記録
- `friend_connection`: ユーザーペア、申請者、関係状態、日時
- `study_plan`: 所有者、予定日、タイトル、詳細、任意カテゴリ、目標問題数
- `question_note` / `question_report`: 本人専用メモ、問題報告と管理者の対応状況
- フレンド対戦の対戦・固定問題・提出結果: 同じ問題セットと参加者ごとの結果を保持

日別・カテゴリ別等の画面は[AnswerRepository](../../src/main/java/jp/co/sss/pr/repository/AnswerRepository.java)の共通集計を利用する。
COUNT/SUMで集計し、全履歴Entityを各画面で別々に数える処理を減らしている。ただし全機能が全履歴取得を廃止したわけではない。

設定:

- 共通の有効プロファイルは現在`product`。ローカル検証用。
- `oracle`は本番用。forward headers処理とSecure Cookie指定を追加済み。
- このプロファイル指定だけではTLS通信は始まらない。外部Tomcatではコンテナー側設定も確認する。
- [現状最新.sql](../db/現状最新.sql)は削除・再作成を含む再構築用。既存データを残す更新には使用しない。
- 同時ログイン列はユーザーから適用済みとの報告あり。現在は再構築SQLにも含まれる。
- 報酬日・メモと報告・対戦・予定の学習条件・当日の達成状態も現状最新の再構築SQLへ統合済み。旧増分SQL15本は、直前バックアップ後に再構築する方針のため削除した。
- 本作業では本番DBへSQLを実行していない。変更後は再ビルド・再起動/再配備が必要。
- 再構築の実行方法は[SQLPlus UTF-8投入手順](../configuration/SQLPlus_UTF8投入手順.md)を参照。バックアップ取得はデータの自動取込みではない。直前のバックアップに増えたユーザー・履歴等があれば、再構築SQLの投入データへ反映するか復元方法を確保する。OracleのDDLは暗黙COMMITがあり、削除はROLLBACKできない。

## 14. 通常テストの出題・採点を順に追う

実装: [TestController](../../src/main/java/jp/co/sss/pr/test_function/TestController.java)、[AnswerGradingService](../../src/main/java/jp/co/sss/pr/service/AnswerGradingService.java)。

### 14.1 出題数と抽出方法

`validCount`で5・10・15以外の出題数を400にする。タブに出題数が未保存なら15を使う。通常のランダム抽出は元リストをコピーしてシャッフルし、希望数を超える場合だけ先頭から切り出す。元のRepository検索結果をそのまま並べ替えるのではない。

```text
候補 = 指定条件に一致した問題
候補のコピーをシャッフル
実出題数 = min(希望出題数, 候補数)
先頭から実出題数を採用
```

候補が7件で10問希望なら7問になる。対象不足を許す通常テストと、希望数不足をエラーにするフレンド対戦は仕様が異なる。

苦手範囲特定の`pickBalanced`は、カテゴリ単位に候補を分けて各グループをシャッフルし、各カテゴリから1問ずつ順に取り出す。希望件数に到達するか、どのグループからも追加できなくなれば終了し、最後に出題順もシャッフルする。カテゴリAが2件・Bが8件なら、Aを使い切った後はBから補う。厳密な同数配分を保証する方式ではない。

### 14.2 解答データの正規化

`normalize(expected, submitted, timeUp)`は次の順で検査する。

1. 出題リスト・送信リストが存在し、件数が一致する。
2. 出題IDにnullや重複がない。
3. 各位置の送信IDがその位置の出題IDと一致する。別問題の差込みや並び替えを許さない。
4. 選択値は1～4。1～3はA/B/C、4は「わからない」。
5. DBから全出題IDを再取得し、欠落がないことを確認する。
6. DBの正答番号が1～3であることを確認する。
7. 問題文・選択肢・カテゴリ・正答・解説をDB値で上書きする。

通常送信ではnullを後段の入力確認へ残すが、null以外の不正な選択値は400。時間切れではnullや範囲外の選択を4へ補正する。出題と一致しないIDや、削除されて欠落した問題は時間切れでも許可しない。

この通常採点は**採点時のDB正答**を使用する。出題後に管理者が問題を編集した場合も、作成時点の内容を固定する対戦スナップショットとは違う。ブラウザーが送った正答番号は信用しない。

### 14.3 採点・保存・結果表示

採点の入口は送信された新しいフォームではなく、タブに保存していた解答・出題を基準にする。途中状態が空ならMyPageへ戻す。未解答nullが残れば400で保存しない。

```text
保存済み解答を再正規化
保存前の履歴から各問題の最新解答を確保
各問題:
  正解 = 選択番号 == DB正答番号
  ANSWERへユーザー・問題・選択・正答・正誤・当日・ANS_COUNT=1を保存
  正解件数を加算
LevelServiceでEXP・満点回数・クエスト・実績を更新
確定後に結果表示用の状態を反映し、結果GETへ移動
```

前回解答は新しい解答を書き込む前の履歴を解答ID降順で走査し、問題ごとに最初の1件を採る。今回の解答が「前回」として表示されないようにする。4や不明値の表示名は「わからない」。

保存済み`CORRECT_FLAG`はその時の正誤記録。結果を閲覧するたびにEXPを付け直すのではない。再読込みに対するPRG、同一タブ直列化、確定後の一時状態整理は別々の役割を持つ。

### 14.4 タイマーの計算

出題開始時に開始ミリ秒と`実出題数 × 25秒`の制限をタブへ保存する。再表示時の残時間は`max(0, 開始時刻 + 制限時間 - 現在時刻)`。7問なら175秒であり、希望10問の250秒ではない。

時間表示は画面側の経過時間計算も併用する。ただし厳格な試験用の期限強制・不正防止機能と同一ではない。ブラウザーJSの変更まで防ぐことを本資料では保証しない。

## 15. 弱点・直近誤答・間隔復習・おすすめの違い

実装: [WeakQuestionService](../../src/main/java/jp/co/sss/pr/service/WeakQuestionService.java)、[StudyReviewService](../../src/main/java/jp/co/sss/pr/service/StudyReviewService.java)、[RecommendationController](../../src/main/java/jp/co/sss/pr/mypage_function/RecommendationController.java)。

### 15.1 問題別の弱点

問題ごとの解答件数が2回以上で、正解件数が解答件数未満の問題を対象にする。率は`正解件数 / 解答件数`のdouble値で比較し、表示の整数パーセントとは分ける。

並び順は次の優先順位。

1. 正答率が低い。
2. 同率なら解答回数が多い。
3. それも同じなら問題IDが小さい。

例: Aが1/4、Bが2/4、Cが1/2なら、A・B・C。BとCの50%は同率だが、Bを先にする。1回しか解いていない問題や全問正解の問題は対象外。最大15問に制限し、採用IDをまとめて再取得する。

### 15.2 直近誤答

本人の履歴を解答ID降順に読み、`seen`集合で問題を一度だけ評価する。最新解答が不正解なら追加し、最新が正解なら古い誤答まで遡って対象へ戻さない。

このため「過去に一度でも間違えた問題」とは異なる。履歴上の最新は解答日の最大値ではなく、検索順の解答IDで判断する。

### 15.3 間隔復習

問題ごとの新しい履歴から、不正解が現れるまでの連続正解を数える。同じ日の連続正解は1日分として数え、同日反復だけで30日後まで間隔を伸ばさない。

| 別日に連続正解した回数 | 最新解答日からの間隔 |
|---:|---:|
| 0（最新が不正解） | 1日 |
| 1 | 1日 |
| 2 | 3日 |
| 3 | 7日 |
| 4 | 14日 |
| 5以上 | 30日 |

`次回日 = 最新解答日 + 間隔`。次回日が今日以前なら期限到来。同日の後の誤答は連続正解を打ち切る。結果は次回日昇順、同日なら問題ID昇順で並ぶ。

### 15.4 おすすめの分岐

条件を順に検査し、最初に該当した提案を採る。機械学習による確率推定ではない。

```text
期限到来の復習がある -> spaced
なければ直近誤答がある -> review
なければ問題別弱点がある -> weak
なければ未学習カテゴリ優先でカテゴリ学習 -> category
出題可能なカテゴリもなければ開始不可の説明
```

カテゴリは実際に問題が存在するものだけを対象にし、未学習を先、同じ区分ならカテゴリID順。未学習の希望難易度は1。既学習なら`min(3, 1 + レベル / 10)`（整数除算）とし、登録済みの有効難易度から希望値に最も近いものを選ぶ。レベル19なら2、20以上なら3。提案は5問を入口にするが、実出題数は対象件数にも依存する。

## 16. EXP・クエスト・実績の更新を計算例で追う

実装: [LevelService](../../src/main/java/jp/co/sss/pr/service/LevelService.java)、[QuestService](../../src/main/java/jp/co/sss/pr/service/QuestService.java)。

### 16.1 行ロックと加算順

顧客が永続化コンテキスト内にいれば悲観書込みロック付きでrefreshし、古い値を読み直す。そうでなければIDから同じロック付きで取得する。古いセッションBeanのEXPをそのまま足して保存する方式ではない。

通常採点では、履歴保存後に満点回数・クエスト判定・獲得EXP・レベル・実績を同じ処理単位で更新する。

```text
満点なら perfect_test_count += 1
獲得EXP = 正解数 * 2
満点なら獲得EXP += 5
当日のクエスト達成状態を記録
全達成かつ本日未付与なら獲得EXP += 10、quest_reward_date = 今日
total_exp += 獲得EXP
user_level = total_exp / 15 + 1
実績条件を検査
```

例: 累計14 EXPで5問すべて正解し、その日のクエスト報酬が未付与なら、10+5+10=25 EXP獲得、累計39、レベル3、レベル内進捗9、次まで6 EXP。同日にもう一度5問満点なら15 EXPで、クエスト10 EXPは重ねない。

### 16.2 達成保持のビットマスク

3つのクエストは5問解答・3問正解・5問以上かつ丸め正答率80%以上。正答率は`Math.round(正解数 * 100.0 / 解答数)`、解答0なら0。最低5問の条件により1問正解だけでは高正答率達成にならない。

達成をビット0・1・2へ対応づける。5問解答だけなら1、5問解答と3問正解なら3、全部なら7。達成日の`quest_progress_date`が今日なら保存済みビットと現在集計を組み合わせる。報酬日が今日なら全達成扱い。

これにより80%達成後に誤答して率が落ちても、その日の達成は消えない。翌日は前日のビットを使わず当日履歴から判定し直す。報酬日・達成日・ビットは役割の異なる3項目。

### 16.3 ログインと実績

同日ログインでは最終アクセス時刻・ログインフラグを更新するが、ログイン日数を増やさず、新規実績リストは空で返す。日付が変わった場合は前日ログインなら連続日数+1、そうでなければ1、累計ログイン日数+1。ログインによるEXP加算はない。

通常実績の条件:

| ID | 解除条件 |
|---|---|
| 1 / 13 | 連続ログイン7日 / 30日 |
| 2 / 3 / 4 / 12 | 満点回数1 / 3 / 7 / 10回 |
| 5 / 7 / 6 / 8 / 9 | レベル10 / 25 / 50 / 75 / 100 |
| 10 / 11 | 累計正解100 / 500問 |
| 14 | 累計ログイン100日 |
| 15 | 問題数が1以上のテストで正解0問 |

実績マスターを取得し、本人の解除記録がなければUSER_ACHIEVEMENTへ保存する。ID15の🌱は表示アイコンで、解除条件は「0問正解」のまま。実績名や絵文字を変えても条件は自動では変わらない。フレンド関連実績16～20は通常実績の上表とは別の処理で扱う。

## 17. 非同期フレンド対戦の固定問題・公開条件・提出

実装: [ChallengeService](../../src/main/java/jp/co/sss/pr/service/ChallengeService.java)。

### 17.1 作成時の検査と保存

本人・相手が利用可能な一般ユーザーであること、相手が自分でないこと、承認済みの関係があることを確認する。カテゴリ・難易度・問題数は必須。難易度1～3、問題数5/10/15以外は業務エラー。

候補からIDや正答番号が不正な問題を除き、希望数に満たなければ不足件数を示して作成しない。足りればSecureRandomを使ってシャッフルし、希望数の問題文・選択肢・正答・解説をFRIEND_CHALLENGE_QUESTIONへコピーする。双方の参加者行も保存する。

通常QUESTIONは後から編集され得るため、対戦中の公平性には固定スナップショットを使う。元問題IDは保存するが、結果維持のため元問題へのFKは設けていない。

### 17.2 公開する情報の段階

| 本人の提出 | 相手の提出 | 状態 | 公開内容 |
|---|---|---|---|
| 未提出 | いずれも | ANSWERING | 問題文・選択肢。正答・解説は渡さない |
| 提出済み | 未提出 | WAITING | 本人の正解件数。相手結果・正答・解説は渡さない |
| 提出済み | 提出済み | COMPLETED | 双方の選択・正誤・正答・解説と勝敗 |

正解数が多い方が勝ち、同数は引き分け。単にHTMLで隠すだけでなく、返すView用recordから非公開情報を除外する。対戦IDを知っていても参加者として確認できなければ詳細を取得できない。

### 17.3 二重提出防止と履歴

顧客行、参加者行の順にロックし、参加者をrefreshして提出済みか再確認する。提出済みなら専用例外。全問題の回答位置が存在し、選択が1～4か検査した後に採点する。

保存は対戦解答、提出件数・時刻、通常解答履歴、EXP・実績を同じトランザクションで行う。対戦正誤はスナップショットの正答で判定する。

元問題が削除されている場合、対戦解答と比較結果は残すが、その問題に対応する通常ANSWERの登録は省略する。EXP計算は対戦全体の結果を使う一方、日別クエストの履歴集計には省略されたANSWERが入らない。この違いを「対戦結果と通常履歴は常に同じ件数」と説明しない。

## 18. メモ・報告・予定の入力検査と所有権

実装: [QuestionStudyService](../../src/main/java/jp/co/sss/pr/service/QuestionStudyService.java)、[StudyCalendarController](../../src/main/java/jp/co/sss/pr/mypage_function/StudyCalendarController.java)。

### 18.1 メモの新規登録と上書き

入力を正規化し、空白だけは拒否、1000文字以内を検査してから問題・本人の存在を確認する。検索キーは本人IDと問題ID。既存行があれば内容と更新時刻を上書きし、なければ作成時刻も付けて新規行を保存する。

メモ削除も本人IDと問題IDの組で行う。他人のメモIDを送信して所有者を変更する方式ではない。DBにもユーザー・問題の一意制約がある。

### 18.2 報告の理由・状態・重複

理由はWRONG_ANSWER / UNCLEAR_EXPLANATION / OTHERの列挙値。未指定・未知の文字列は拒否する。説明は1000文字以内、OTHERだけは説明必須。理由が他の2種類なら空説明をnullで保存できる。

本人・問題・理由・OPENが同じ報告があると重ねて受け付けない。RESOLVEDやON_HOLDはこのOPEN重複チェックの対象ではない。新規報告はOPEN、作成時刻・更新時刻を同時に設定する。

管理者一覧は20件単位、作成時刻降順・同時刻なら報告ID降順。負のページは0、存在しない大きなページは最終ページへ丸める。状態変更は有効な列挙値と対象存在を確認して更新時刻も変更する。

`QuestionStudyException`は想定内の入力エラーとして`noRollbackFor`で区別する。DB障害まで成功扱いにするものではない。共有フィルター内トランザクションとの関係は第4章を参照。

### 18.3 学習予定と月表示

予定は本人に紐づけて保存する。タイトル100文字、詳細500文字の制限、目標数5/10/15を検査。カテゴリは任意だが、指定時は存在を確認する。失敗時はFlashメッセージで同じ月・日へ戻し、保存しない。

編集・削除は対象予定が本人のものか検査する。画面で他人の予定を見せないだけではなく、操作時も所有権確認を行う。

表示月と選択日が食い違えば、今月なら今日、他月なら月初へ補正する。編集対象があればその予定の月・日を優先する。月内の履歴を日別集計、月内予定を日別件数に変換し、選択日の詳細は別に取得する。表示する不正解数は`解答数 - 正解数`。

## 19. 週間推移の集計と「データなし」

実装: [LearningTrendService](../../src/main/java/jp/co/sss/pr/service/LearningTrendService.java)。

今日の属する週の月曜日から7週前を開始日にし、当週を含め8週を作る。開始前・今日より後・日付nullの集計行は除外する。

`週番号 = (学習日の通算日 - 開始日の通算日) / 7`で0～7の配列へ解答・正解数を加算する。過去週は日曜日まで、当週は今日までなので、当週の途中集計と前週の全週を比較している点に注意する。

正答率は解答0ならnull。解答ありなら丸めた正解割合。今週か前週のどちらかがnullなら正答率差もnullで、「観測なし」を0%と混同しない。解答件数差は今週－前週。

棒の長さは8週内の最大解答数を100%として相対計算する。最大値を最低1にしてゼロ除算を避ける。棒が100%だから正答率100%という意味ではない。
